# مراجعة المخططات قبل التنفيذ

تمت قراءة README وCODEX_TASK والمخططات السبعة وضوابط التنفيذ. لا يوجد AGENTS.md في شجرة المستودع عند بداية العمل. تبقى المخططات الأصلية دون تغيير.

## نواقص وتعارضات تستلزم قرارًا موثقًا

- لم تحدد العملة أو أصغر وحدة أو دقة الكميات. حقول decimal التصورية غير كافية لتحديد التخزين والتقريب.
- InventoryBatch يفتقد كمية الدفعة وقيمتها الإجمالية؛ لا يمكن التحقق من مساواة الدفعات بالاستلام أو حفظ فروق التقريب بدونهما.
- فواتير البيع والتحويل والمرتجعات تفتقد المستودع وتخصيص الدفعات. البيع النقدي لا يملك طريقة تسوية واضحة عند غياب العميل.
- الاعتماد والترحيل والسداد حالات مختلفة، بينما معظم المستندات لا تحتوي حالة أو مرجع قيد. المصروف والراتب يحتاجان حدثي استحقاق وسداد مستقلين.
- أهلية EXPENSE للشحن غير ممثلة بحقل. توقيت وصول الشحن بعد استهلاك المخزون وتكاليف إعادة تقييمه غير محدد.
- مصادر المخزون والقيود متعددة الأشكال ليست مفاتيح أجنبية. يلزم مرجع مصدر حقيقي ومنع إعادة اعتماد المصدر.
- الحسابات المقابلة للمخزون والذمم والإيراد والرواتب والإهلاك غير محددة. لا توجد قواعد ضرائب أو خصومات أو عملات متعددة أو طريقة إهلاك متفق عليها.
- مرتجع بعد قبض/سداد قد يولد رصيدًا مقدمًا، لكن لا توجد سياسة رد نقدي. تسوية عجز النقل والإلغاء بعد الاعتماد ليست محددة.

## قرارات التنفيذ لهذه النسخة التجريبية

- عملة واحدة قابلة للتسمية عند الإنشاء، بمقياس 100 وحدة صغرى للوحدة الكبرى في seed التجريبي، دون افتراض عملة بلد. الكمية بعدد صحيح من أجزاء الألف. لا تقبل API float. التقريب HALF_UP؛ المبالغ وقيم المخزون INTEGER ضمن حدود 64 بت. تغيير المقاييس بعد إنشاء المستندات غير مدعوم.
- إضافة Quantity وTotalCost للدفعة. TotalCost هو المرجع الدقيق؛ UnitCost معلومة مقربة. توزيع التكلفة والشحن على الاستلامات والدفعات بالفرق بين النسب التراكمية المقربة؛ الباقي يصل إلى آخر دفعة. لا تحمل الكمية غير المستلمة على المخزون. الشحن اللازم للوصول INVENTORY؛ EXPENSE يتطلب أهلية وسببًا صريحين. يعتمد الشحن قبل أول استلام؛ إعادة تقييم مخزون مستهلك عمل لاحق يحتاج سياسة ومراجعة، ولذلك يرفض النظام الإضافة المتأخرة.
- كل مخزون متتبع بالدفعات؛ صرف FIFO حسب BatchID مع حفظ الكمية والتكلفة المصروفة لكل دفعة في StockAllocation. تكلفة الصرف من القيمة المتبقية في الموقع، وآخر صرف يأخذ الباقي. لا يسمح بمخزون سالب. رقم المصنع غير فريد.
- حالات المستندات DRAFT ثم POSTED فقط؛ التحويل يشحن مرة وتستلم منه أجزاء متعددة، والجزء الباقي قيد النقل. لا حذف أو تعديل للآثار المعتمدة. التصحيح العكسي متاح للقيد اليدوي فقط؛ عكس مستند آلي منفردًا سيخل بدفتره المساعد، ولذلك يتطلب إجراءً إضافيًا غير منفذ هنا. لا توجد إجازة تلقائية لتجاوز الطلب.
- البيع النقدي يقيد مباشرة إلى حساب مالي؛ الآجل يتطلب عميلًا. القبض والسداد يسمحان برصيد مقدم غير موزع؛ التوزيع لا يتجاوز الصافي بعد المرتجعات والتوزيعات السابقة. المرتجع النقدي المعتمد يرد إلى الحساب الأصلي، أما الآجل فيخفض الذمة. يرفض المرتجع الذي سيجعل التوزيعات الحالية تتجاوز صافي الفاتورة إلى حين تسوية مخصصة. تطبيق المقدمات لاحقًا أو رد الزيادة يحتاج مستند تسوية جديدًا؛ لا تعدل التخصيصات المعتمدة.
- جدول AccountingPolicy يحدد الحسابات المقابلة. قيد شراء عند اعتماد الفاتورة: بضائع قيد الاستلام/دائن المورد؛ قيد الاستلام ينقل التكلفة إلى المخزون. شحن INVENTORY يقيد إلى قيد الاستلام، وEXPENSE إلى المصروف. فرق تكلفة الشحن غير المسترد في مرتجع الشراء يسجل في حساب فروق المخزون. لا يكرر السداد استحقاق المصروف أو الراتب؛ جدول ExpensePayment يتيح السداد اللاحق دون تعديل المصروف المعتمد. استحقاق الراتب بالصافي؛ توزيع الاستقطاعات يحتاج سياسة مستقلة. رسوم التوصيل تقيد عند اعتماد التوصيل وتدخل في المستحق القابل للتخصيص، ولا تسترد تلقائيًا مع الأصناف.
- الإهلاك الخطي يبدأ بشهر الشراء دون تجزئة الشهر، وعلى أشهر تقويمية متتابعة. يعتمد على فرق القيمة المستهدفة التراكمية المقربة عن السابق مع سقف Cost-SalvageValue؛ يحفظ حدثًا دون قيد مالي إذا كان الفرق صفرًا. الاستبعاد يسجل الأصل ومجمع الإهلاك والمتحصل والربح أو الخسارة. لا ضرائب أو عملات متعددة مفترضة، ولا منع تلقائي لرصيد نقدي دائن دون سياسة سحب/تمويل متفق عليها.
- جدول PostingEvent يربط كل حدث بمصدر واحد عبر FK حقيقي وCHECK لاختيار مصدر واحد. المخزون والحركة المالية والقيد تشير إلى الحدث. SourceType/SourceID حقول متوافقة مع المخطط تتحقق منها triggers. الترحيل يتم من خلال API محكومة ومعاملة BEGIN IMMEDIATE واحدة؛ لا يمنح التطبيق منفذ SQL حرًا. القيود المحلية ومراجع المصادر وحماية الآثار المرحلة تفرض أيضًا في SQL. يجب على أي كاتب آخر الالتزام ببروتوكول الترحيل نفسه.
- هذه قرارات تنفيذ تجريبية معلنة للمراجعة وليست اعتمادًا لسياسة مالية إنتاجية. حماية ملفات SQLite والصلاحيات التشغيلية على مسؤولية التطبيق المضيف؛ جداول الأدوار لا تحل محل مصادقة التطبيق.
