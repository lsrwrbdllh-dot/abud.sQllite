# خطة الانتقال إلى SQL Server

يبقى منطق الأعمال ووحدات التخزين ومفاتيح منع التكرار ثابتة. لا تشغل SQL الخاص بـSQLite على SQL Server مباشرة، ولا تحول الأموال إلى FLOAT أو MONEY ضمن عملية النقل. هذه خطة فروق وخطوات، وليست ادعاءً بتنفيذ ترحيل SQL Server أو اختباره.

## الأنواع

| SQLite الحالي | SQL Server المقترح | ملاحظات |
| --- | --- | --- |
| INTEGER PRIMARY KEY | BIGINT IDENTITY(1,1) PRIMARY KEY | احتفظ بالمعرفات عبر IDENTITY_INSERT عند النقل؛ لا تعتمد على إعادة استخدامها |
| INTEGER مبلغ/كمية | BIGINT | نفس المال بوحدات صغرى والكمية بأجزاء الألف؛ استخدم DECIMAL(38,0) مؤقتًا للضرب والتجميع ثم تحقق من حدود BIGINT |
| INTEGER علم 0/1 | BIT | احتفظ بمنطق CHECK عند تحويله |
| TEXT اسم/وصف | NVARCHAR(n) أو NVARCHAR(MAX) | احتفظ بالعربية واختر أطوالًا بعد تحليل البيانات |
| TEXT تاريخ ISO-8601 | DATE | تحقق مسبقًا عبر TRY_CONVERT؛ لا تقبل تاريخًا غير صالح |
| TEXT وقت UTC | DATETIME2(0) | الاتفاق أن القيمة UTC؛ بديل DATETIMEOFFSET(0) عند الحاجة لحفظ الإزاحة |
| PasswordHash | NVARCHAR(512) | احفظ السلسلة المرمزة كاملة ولا تعيد تشفيرها ولا تصدر كلمات مرور |
| OldValues/NewValues JSON نص | NVARCHAR(MAX) مع ISJSON | NULL مسموح عند غياب قيمة؛ ليس تغييرًا للبيانات المالية |

`STRICT` وPRAGMA خاصان بـSQLite؛ SQL Server يفرض الأنواع بالـDDL. راجع حساسية حالة الأحرف: SQLite NOCASE في Username محدود مقارنة بcollation SQL Server؛ حدد سياسة تطبيع أسماء المستخدمين وافحص التعارضات قبل النقل. Hashes حساسة لحالة الأحرف.

## القيود والفهارس والمصادر

- انقل جميع PK وFK وCHECK. جداول PostingEvent وStockAllocation تستخدم مراجع FK حقيقية إلى مصادر منفصلة؛ تستمر قاعدة اختيار مرجع واحد فقط، وتتحول أعلام IS NOT NULL في CHECK إلى CASE WHEN ... THEN 1 ELSE 0 END.
- SQLite يسمح بعدة NULL في UNIQUE، بينما UNIQUE في SQL Server قد يعامل NULL بطريقة مختلفة. استخدم filtered unique indexes للأعمدة الاختيارية: AssetDepreciation.JournalEntryID وAssetDisposal.JournalEntryID وJournalEntry.ReversesJournalEntryID، مع `WHERE column IS NOT NULL`، وباقي الأعمدة الاختيارية الفريدة إن أضيفت لاحقًا. تبقى المفاتيح المركبة غير الفارغة العادية كما هي.
- أنشئ فهارس FK ومفتاح المصدر SourceType/SourceID/SourceEvent، ومفتاح EventID/FinancialAccountID. SQL Server لا يضيف فهرسًا لكل FK تلقائيًا. لا تضف ON DELETE CASCADE إلى البيانات المالية أو المخزنية؛ الحذف التاريخي يظل ممنوعًا.
- لا يوجد بديل لمجرد افتراض FK للزوج المنطقي؛ يجب نقل تحقق تطابق SourceType مع المرجع المختار، وتحقق ملكية تفاصيل المستندات، وتطابق المصدر والدفعة والمخزن.
- انقل StockInTransit كـVIEW بنفس دلالة الاعتماد الفعلي. احتفظ بـSchemaMigration وأضف إصدارات جديدة؛ لا تعيد تشغيل 001 على قواعد مستخدمة.

## المعاملات وtriggers

- `BEGIN IMMEDIATE` يحجز كاتب SQLite واحدًا. في SQL Server استخدم إجراءات ترحيل مخزنة أو طبقة خدمة داخل transaction بمستوى SERIALIZABLE، أو أقفال UPDLOCK/HOLDLOCK على أسطر الكمية/الرصيد/التسوية ومفاتيح نطاقها قبل التجميع. قفل على صف واحد موجود فقط لا يحمي من إدخال استلام أو تخصيص منافس جديد؛ يجب حماية النطاق والمفتاح أيضًا. ضع ترتيب أقفال ثابتًا، وأعد محاولة deadlock على العملية كاملة بمفتاح idempotency نفسه.
- استخدم SET XACT_ABORT ON وTRY/CATCH مع ROLLBACK وTHROW. لا تبتلع الخطأ ولا تعتمد قيدًا بعد فشل المخزون. انقل معاملات الخدمة التي تتحقق من الاستلام والشحن والمرتجعات وحدود تخصيص النقد والرواتب والإهلاك؛ وجود SQL DDL وحده لا ينفذ هذه القيود التجميعية.
- triggers في SQLite تعمل لكل صف وتستخدم NEW/OLD وRAISE(ABORT). SQL Server يستخدم inserted/deleted وقد تضم عدة صفوف: أعد كتابة كل trigger بمنطق مجموعات وفحوصات مجمعة وTHROW. تجنب نمط اختيار صف واحد من inserted، ولا تفترض دعم BEFORE؛ حدد INSTEAD OF أو AFTER وفق الحماية المطلوبة.
- تحديث BatchStock وInventoryBalance من InventoryMovement يجب أن يجمع دلتا كل دفعة ومنتج ثم يحدث الأرصدة في المعاملة نفسها مع منع السالب. لا تستبدل UPSERT في SQLite بـMERGE دون معالجة السباقات؛ UPDATE محمي بالأقفال ثم INSERT محمي عادة أوضح.
- استبدل strftime وdate validation بـDATE/DATETIME2 والتحويل عند الإدخال، وأعد كتابة فحص دورات شجرة الحسابات بـCTE مناسب مع منع recursion غير المنتهية.
- استخدم OUTPUT INSERTED.ID لالتقاط المعرفات. SAVEPOINT في SQLite يصبح SAVE TRANSACTION؛ انتبه إلى XACT_STATE()، فبعض الأخطاء تجعل المعاملة غير قابلة للاعتماد ويجب التراجع عن العملية العليا كاملة.
- أمن SQL Server عبر حساب خدمة محدود ينفذ إجراءات الترحيل؛ لا تمنحه تعديل الأرصدة والآثار مباشرة. نفذ صلاحيات التطبيق وأثر المستخدم في AuditLog؛ لا تعتبر جداول الأدوار مصادقة مكتملة.

## خطوات النقل والتحقق

1. ثبت إصدار المخطط وسياسات الحسابات والعملة والكميات، واختبر نسخة احتياطية قابلة للاستعادة. أوقف الكتابة أثناء اللقطة النهائية.
2. نفذ `PRAGMA integrity_check` و`foreign_key_check` و`Database.check()`، وافحص المسودات والأحداث غير المكتملة والتكرارات والتواريخ و64 بت. أصلح التعارضات بإجراءات موثقة قبل النقل.
3. أنشئ مخطط SQL Server ضمن بيئة تجريبية، وانقل البيانات بترتيب الآباء ثم الأبناء وبالمعرفات الأصلية. العلاقات الدائرية JournalEntry/AssetDepreciation/PostingEvent تستدعي إنشاء الجداول ثم إضافة FK، أو تحميلًا مرحليًا مضبوطًا وإعادة تفعيل كل القيود مع WITH CHECK CHECK CONSTRAINT.
4. قارن عدد الصفوف لكل جدول وhashes نصوصه بعد التطبيع المتفق عليه، ومجاميع المال والكمية بدقة صحيحة. قارن المخزون حسب المستودع والمنتج والدفعة مع مجموع الحركات، وقيد النقل مع التحويلات غير المستلمة، وقيم تكلفة الاستلام والشحن، وأرصدة الحسابات المالية مع قيود الأحداث.
5. أعد تنفيذ السيناريوهات الـ35 على adapter لـSQL Server مع اختبارات تنافس مستقلة للاستلام والتحويل والسداد والمرتجعات وإغلاق الفترات. اختبر إدخالات متعددة الصفوف في triggers ومفاتيح NULL الفريدة والتراجع عن العمليات الفاشلة. لا تكفي نتيجة اختبارات SQLite لاعتماد المحرك الجديد.
6. نفذ مراجعة مالية وتقنية مستقلة، ثم قطع التحويل بخطة رجوع واضحة. تجنب الكتابة المتزامنة في المحركين دون بروتوكول تزامن مستقل. احتفظ بالمصدر والنسخة الاحتياطية وسجل تحقق النقل.
