# تشغيل قاعدة البيانات ومراجعتها

هذا تنفيذ SQLite للمخططات الأصلية: 68 جدولًا، مع مفاتيح أجنبية فعلية ومبالغ صحيحة وترحيل محكوم. راجع [تقرير القرارات](../docs/design-review.md) أولًا؛ يتضمن السياسات التي لم تحددها المخططات. لا توجد اعتماديات Python خارج المكتبة القياسية.

## Codespaces، بما في ذلك من الجوال

1. افتح المستودع على GitHub في المتصفح واختر فرع Pull Request `codex/sqlite-accounting`.
2. اختر **Code → Codespaces → Create codespace on codex/sqlite-accounting**. على الجوال قد تحتاج وضع «موقع سطح المكتب» لإظهار القائمة والطرفية.
3. انتظر تجهيز البيئة المحددة في `.devcontainer/devcontainer.json` وافتح **Terminal → New Terminal**. تنفذ البيئة الاختبارات تلقائيًا عند التجهيز؛ يمكنك تكرارها بالأمر أدناه.
4. نفذ الأوامر التالية من جذر المستودع. المطلوب Python 3.12 وSQLite 3.37 أو أحدث لدعم STRICT؛ صورة Codespaces المرفقة مناسبة. لا تحتاج تثبيت SQL Server أو تشغيل خادم ويب.

```bash
python -m unittest discover -s tests -v
python -m database.engine supermarket.sqlite --seed
python -m database.demo supermarket-demo.sqlite
```

الأمر الثاني ينشئ المخطط وبيانات أساسية افتراضية فقط؛ الأمر الثالث ينشئ ملفًا مستقلًا فيه 20 حدثًا تجريبيًا تشمل البيع والقبض والاستلام والشحن والتحويل والمرتجع والراتب والإهلاك. يرفض demo الكتابة فوق ملف موجود. يمكن تنزيل ملف SQLite من لوحة Explorer بزر Download في Codespaces وفتحه بعارض SQLite على الجوال. GitHub يعرض الملفات ولا يشغل قاعدة البيانات بنفسه. لا ترفع بيانات حقيقية أو ملفات قاعدة البيانات إلى Git؛ `.gitignore` يستبعدها.

لإعادة فتح قاعدة سبق إنشاؤها وفحصها دون إعادة seed:

```bash
python -m database.engine supermarket.sqlite
```

`--seed` للاستخدام مرة واحدة على قاعدة فارغة؛ التكرار يرفضه UNIQUE وترجع معاملة seed بالكامل. لا يحذف البرنامج البيانات الموجودة. النسخ الاحتياطي يكون عبر SQLite backup API عند إغلاق الكتابات، وليس بنسخ ملف نشط دون تنسيق.

## ملفات SQL المستقلة

يمكن استخدام sqlite3 CLI إن كان مثبتًا:

```bash
sqlite3 -bail supermarket-sql.sqlite < database/migrations/001_initial.sql
sqlite3 -bail supermarket-sql.sqlite < database/seed.sql
sqlite3 supermarket-sql.sqlite 'PRAGMA foreign_keys=ON; PRAGMA foreign_key_check; PRAGMA integrity_check;'
```

كل سكربت يشمل PRAGMA وBEGIN IMMEDIATE وCOMMIT. عند خطأ من التطبيق ينفذ ROLLBACK؛ عند تشغيل CLI استخدم `-bail` ليتوقف ويغلق الاتصال دون اعتماد جزء من المعاملة. الترحيل ليس سكربت reset ولا يعاد مباشرة على مخطط موجود. `Database.migrate()` يفحص SchemaMigration ويطبق الإصدار الأول مرة واحدة. ملف SQL مولّد ومثبت في Git؛ لتعديل المخطط عدل `database/build_schema.py` ثم شغله، وأضف ترحيلًا جديدًا إذا كانت هناك قاعدة منشورة. اختبار آلي يضمن تطابق SQL مع مولده.

## التعامل مع التطبيق

```python
from database.engine import Database, money, quantity

db = Database('supermarket.sqlite')
try:
    db.migrate()
    # قاعدة جديدة فقط: db.seed()
    with db.transaction():
        invoice = db.add('PurchaseInvoice', SupplierID=1,
                         BranchID=1, InvoiceDate='2026-01-02')
        db.add('PurchaseInvoiceDetail', PurchaseInvoiceID=invoice,
               ProductID=1, Quantity=quantity('2.5'), UnitPrice=money('8.00'))
        db.post('PurchaseInvoice', invoice)
    db.check()
finally:
    db.close()
```

هذا يثبت استحقاق فاتورة الشراء فقط. أنشئ GoodsReceipt ثم GoodsReceiptDetail وInventoryBatch، وبعد ذلك `db.post('GoodsReceipt', receipt_id)` لتدخل البضاعة فعليًا. يحتوي demo على أمثلة مكتملة. الدوال العامة `add` للمسودات والبيانات الأساسية، و`post` للاعتماد، و`freeze_count` لتثبيت لقطة الجرد، و`manual_entry` للقيد اليدوي. جميعها تستخدم BEGIN IMMEDIATE مع SAVEPOINT للعمليات المتداخلة وROLLBACK عند أي استثناء. كل اتصال `Database` يفعّل foreign_keys وbusy_timeout؛ على أي اتصال خارجي تفعيل foreign_keys أيضًا.

لا تعرض `conn` أو `_insert` أو SQL حرًا لمستخدم التطبيق. هي أدوات داخلية موثوقة؛ لا تمنع SQLite مالك الملف من تعديل SQL أو إسقاط triggers. القيود التجميعية العابرة للمستندات تستخدم خدمة الترحيل داخل المعاملة؛ لا تنفذ اعتماد المستند بإرسال UPDATE من عارض قواعد البيانات. `add` يرفض إنشاء الحركة أو الرصيد أو القيد مباشرة. لا توجد واجهة HTTP أو نظام دخول هنا؛ التطبيق المضيف مسؤول عن التحقق من هوية المستخدم وتطبيق Role/Permission على أوامره. `PasswordHash` يقبل صيغ hashes معروفة فقط؛ لا يوجد حساب دخول افتراضي، ولا تحفظ كلمة مرور خام. AuditLog يسجل الاعتماد النظامي وهو غير قابل للتعديل؛ ربط هوية المستخدم وتدقيق تعديلات المسودات مسؤولية التطبيق المضيف.

## وحدات التخزين والتكلفة

- SystemSetting يثبت عملة تجريبية واحدة DEMO بمقياس 100. `money('12.34') = 1234`، و`quantity('2.5') = 2500`. تغيير المقاييس غير مدعوم، ولا يفترض اسم عملة حقيقية. جميع المبالغ والكمية INTEGER، ولا يوجد REAL في المخطط. التحويل يستعمل Decimal وتقريب HALF_UP؛ float مرفوض.
- قيمة السطر = تقريب `Quantity * UnitPrice / 1000`. Python ينفذ الضرب بدقة صحيحة ثم يتحقق من حدود 64 بت قبل التخزين. TotalCost هو تكلفة الدفعة الدقيقة، وUnitCost تقريب إيضاحي فقط.
- يوزع مجموع قيمة سطر الشراء وشحنه INVENTORY على كميات الاستلام بالفرق بين نسبتين تراكميتين مقربتين. مثال تكلفة 401 على ثلاث وحدات: 134 ثم 133 ثم 134. بعد أول استلام جزئي تبقى تكلفة الكمية غير المستلمة في حساب قيد الاستلام.
- يلزم اعتماد الشحن كاملًا قبل أول استلام. EXPENSE يحتاج أهلية وسببًا، ولا يقبل أي توزيع. لا يدعم هذا الإصدار إعادة تقييم شحن يصل بعد الاستلام، أو تكاليف مباشرة أخرى خارج الشحن؛ يرفض السيناريو غير المدعوم بدل تعديل تكلفة مخزون مستهلك.
- الصرف FIFO حسب معرف الدفعة، من تكلفة الكمية المتبقية في الموقع مع استهلاك فرق التقريب في آخر صرف. المرتجع البيعي يعيد دفعات البيع الأصلية وتكلفتها. الشحن يحتفظ بمعرف الدفعة عبر النقل؛ ManufacturerLot مستقل وقد يتكرر.
- الاستلام والتحويل والمرتجع يراعي المستندات POSTED فقط؛ المسودة لا تحرك مخزونًا أو نقدًا. لا مخزون سالب. التحويل يصرف عند الشحن ويضيف عند كل استلام فعلي؛ `StockInTransit` يعرض الكمية الباقية. عجز النقل لا يسوى تلقائيًا.

## الضوابط ومكان فرضها

| الضابط | التنفيذ |
| --- | --- |
| FK، UNIQUE، أعداد صحيحة، مبالغ موجبة، تواريخ ISO، ملكية أسطر المستند | SQL STRICT وCHECK وFK وtriggers |
| مصدر فعلي لكل حدث، وتوافق SourceType/ID | PostingEvent بمرجع FK واحد مختار عبر CHECK وtriggers؛ ليس FK متعدد الأشكال |
| مصدر سطر المخزون وتوافق الحدث والدفعة والحركة | StockAllocation بمراجع حقيقية، وInventoryMovement بمرجع تخصيص فريد |
| منع تكرار ترحيل المستند والحركة المالية | UNIQUE للمصدر/المعرف/الحدث وللحدث/الحساب، وحالة المستند المقفلة |
| توازن القيد، سطران على الأقل، حسابات تسمح بالترحيل، سنة وفترة مفتوحتان والتاريخ داخلهما | triggers عند الانتقال إلى POSTED |
| عدم تغيير أو حذف المستند/القيد/الأثر المرحل، أو إضافة أسطر له | triggers، مع قيد عكسي مرتبط للقيد اليدوي |
| مجموع الدفعات = المستلم؛ حدود الاستلام والتحويل والمرتجعات؛ تطابق المنتج والمستودع | خدمة `post` ومعاملة BEGIN IMMEDIATE |
| أهلية الشحن وتوزيعه الكامل وتوقيت اعتماده | CHECK وملكية SQL، ثم تحقق تجميعي في `post` |
| حدود القبض والسداد وصافي المستحق بعد التسويات | `post` داخل المعاملة؛ المتبقي من الدفع رصيد مقدم |
| صرف المخزون وتحديث رصيد الدفعة والمنتج معًا | trigger الحركة داخل معاملة الاعتماد؛ فحص عدم السالب |
| اكتشاف خلل الأرصدة | `check`: سلامة SQLite وFK وتوازن القيود ومطابقة أرصدة الدفعات والحركات والحسابات المالية |

المستند ذو الأثر النقدي يتطلب FinancialAccountID. المصروف غير المدفوع يستحق دون حركة نقدية؛ للسداد اللاحق أنشئ ExpensePayment مع ExpenseRef أو DeliveryExpenseRef، ولا تعدل المصروف المعتمد. إذا حدد حسابًا ماليًا عند إنشاء المصروف، يولد اعتماده حدث استحقاق وحدث سداد منفصلين داخل معاملة واحدة. SalaryPayment يسدد الرواتب المستحقة دون تكرار مصروفها. الاستحقاق هنا بقيمة NetSalary؛ توزيع الاستقطاعات على التزامات مستقلة يحتاج سياسة إضافية.

قيد يدوي يصحح بقيد عكسي موثق من `manual_entry(..., reversal_of=journal_id)` يطابق الأسطر المعكوسة. عكس مستند أعمال آلي يتطلب تصحيح دفاتره المساعدة أيضًا؛ لا يسمح API بعكس قيده وحده. يسمح هذا الإصدار بإنشاء تخصيصات القبض/السداد قبل اعتماد السند؛ تطبيق رصيد مقدم قديم لاحقًا يحتاج مستند تسوية إضافيًا غير منفذ هنا، ولا تعدل تخصيصًا معتمدًا.

## مصفوفة المعالجة المحاسبية

| الحدث | مدين | دائن |
| --- | --- | --- |
| اعتماد الشراء | بضائع قيد الاستلام | المورد |
| شحن INVENTORY / EXPENSE | قيد الاستلام / المصروف | المورد |
| استلام الشراء | المخزون بالتكلفة المحملة | قيد الاستلام |
| البيع | الصندوق أو العميل؛ تكلفة المبيعات | المبيعات؛ المخزون |
| القبض / سداد المورد | الصندوق / المورد | العميل / الحساب المالي |
| صرف تحويل / استلامه | قيد النقل / المخزون | المخزون / قيد النقل |
| المرتجع البيعي | المبيعات؛ المخزون الأصلي | العميل أو رد نقدي؛ تكلفة المبيعات |
| مرتجع شراء | المورد بسعر الشراء؛ فرق التكلفة إن وجد | المخزون بالتكلفة المحملة؛ فرق التكلفة إن وجد |
| استحقاق مصروف / راتب | المصروف أو صافي الرواتب | التزام مستحق |
| السداد | الالتزام المستحق | الحساب المالي |
| توصيل | الصندوق أو العميل | إيراد رسوم التوصيل |
| شراء أصل / إهلاكه | الأصل / مصروف الإهلاك | الحساب المالي / مجمع الإهلاك |

لا يرد شحن المشتريات تلقائيًا عند مرتجع الشراء؛ فرق التكلفة المحملة يسجل في حساب فروق المخزون. مرتجع البيع النقدي يرد القيمة إلى الحساب المالي الأصلي، أما الآجل فيخفض الذمة. يرفض مرتجع يجعل التخصيصات السابقة أعلى من صافي الفاتورة؛ يلزم إجراء تسوية مخصص لم ينفذ هنا. رسوم توصيل معتمدة تدخل في صافي الفاتورة القابل للقبض، ولا ترد تلقائيًا عند مرتجع الأصناف.

الإهلاك خطي على فترات أشهر تقويمية متتابعة بدءًا من شهر الشراء دون تجزئة الشهر: المستهدف التراكمي = تقريب `(Cost-SalvageValue)*عدد الأشهر/UsefulLifeMonths`، وقيد الشهر هو الفرق عن الإهلاك السابق. قد يكون الفرق صفرًا للأصول الصغيرة؛ يحفظ الحدث دون قيد صفري. لا يتجاوز الإجمالي القيمة القابلة للإهلاك، ولا يعتمد إهلاك بعد الاستبعاد. الاستبعاد يسجل المتحصل ومجمع الإهلاك وإزالة الأصل والربح/الخسارة. هذه سياسة تجريبية موثقة للمراجعة، ولا توجد ضرائب أو عملات متعددة أو تجاوزات طلب معتمدة تلقائيًا.

## الاختبارات ونتائج التنفيذ

شغلت الاختبارات في بيئة العمل على Python 3.12.14 وSQLite 3.53.1 بتاريخ 2026-10-21: **35 اختبارًا ناجحًا**. تشمل السيناريوهات المطلوبة، جميع الـ156 FK في نسخة اختبار معزولة، rollback كاملًا عند الرفض، تنافس اتصالين على بيع آخر كمية، الإهلاك والتقريب على مبالغ صغيرة، وتطابق SQL المولد. اختبار FK المعزول يعطل triggers وCHECK في نسخة مؤقتة فقط كي يتأكد أن كل FK نفسه يرفض المرجع اليتيم؛ بقية الاختبارات تستخدم كل القيود دون تعطيل.

شغل المثال الكامل بنجاح: **20 حدثًا** مع `integrity_check=ok` و`foreign_key_check` دون أخطاء. أضيف GitHub Actions لتشغيل الاختبارات وإنشاء قاعدة seeded عند push وPull Request. لم تفتح جلسة Codespaces فعلية أثناء التنفيذ؛ أوامر التشغيل واختباراتها لا تحتاج اعتماديات إضافية، ونتيجة CI الخاصة بالـPR تظهر على GitHub عند تشغيلها. راجع [خطة SQL Server](../docs/sql-server-migration.md) قبل تغيير المحرك.
